## Problema

El POS web de CasaMarket emite Boleta, Factura y Nota de Venta ante SUNAT para clientes que venden 24/7, así que rehacer su flujo de venta no podía fallar.

El trabajo tenía dos partes: llevar la lógica de venta a una capa que se pudiera probar, y demostrar que el flujo nuevo produce lo mismo que el anterior.

## Decisión

Diseñé una capa de dominio pura y testeable (carrito, pagos, cliente, crédito, impuestos y descuentos) con la venta como caso de uso.

Para comprobar el flujo nuevo ideé una estrategia de paridad. Una suite E2E en Playwright ejecuta la misma venta en el POS legacy y en el nuevo, captura los dos payloads y los compara campo por campo. Ignora el ruido conocido, como fechas e IDs.

<ParityDiagram lang="es" />

Usé Claude Code para auditar el código en paralelo y generar casos de prueba. El alcance, las reglas de negocio y la validación de los hallazgos los definí yo.

## Resultado

Son 12 suites: precisión decimal, tipos de impuesto, descuentos, combos y pagos, entre otras. El nuevo flujo de venta está en producción.

## Límite

La paridad no prueba que el cálculo sea correcto. Si los dos sistemas comparten un bug, el test pasa igual. Dejé documentado este límite del método.
